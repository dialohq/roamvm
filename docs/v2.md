# Experimental v2 operator

The experimental operator serves `v2.vm.roamvm.io/v1alpha1` (`rvm2`). The
existing operator continues serving `vm.roamvm.io/v1alpha1` (`rvm`). These are
separate resources, not served versions of one CRD. Neither operator adopts the
other's VMs. Legacy migration is not implemented.

## Install alongside the existing operator

Build the opt-in image with `docker build --target v2 -t YOUR_IMAGE .` and publish
it, then use a Kustomize overlay
over `config/v2` to set both the controller image and its `RUNNER_IMAGE` environment
variable to that image's digest. The checked-in `roamvm:dev` is a development tag.
Do not replace the legacy installation or its runtime configuration.
The default Docker target keeps the legacy packaged QEMU. The `v2` target and
Nix runtime include the pinned RoamVM QEMU extension required for private RAM
checkpoints; a new hibernating guest refuses an unsupported hypervisor before
executing guest CPUs.

```sh
kubectl apply --server-side -k config/v2
```

The v2 deployment runs `roamvm --experimental-v2 controller` in
`roamvm-v2-system`, with its own leader lease and RBAC restricted to the v2 VM
group. The flag is propagated to runners, daemons and checkpoint workers. Normal
CLI commands still select the legacy API; prepend `--experimental-v2` for v2
`start`, `stop`, `state` and `recover` commands.

Provision `default/roamvm-v2-object-store` through your secret manager before
creating VMs. Required keys are `S3_BUCKET`, `AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`; optional keys are `S3_ENDPOINT`, `AWS_REGION` and
`AWS_SESSION_TOKEN`. Do not put credentials in the public manifests.

`default/roamvm-v2-runtime` defaults to `STATE_BACKEND=kubernetes` and
`STATE_NAMESPACE=roamvm-v2-system`: Garage does not support the conditional writes
required for S3 ownership metadata. Back up that namespace's state ConfigMaps
alongside the bucket. Do not switch a VM's metadata backend after creation.

For another VM namespace, provision the v2 runtime ServiceAccount, daemon
RoleBinding, runtime ConfigMap and Secret there, and add that account to the
state RoleBinding in `roamvm-v2-system`. The controller reads only the named
runtime configuration and Secret when performing deletion cleanup. Keep them
available until all VMs have been deleted.

## Storage and hibernation

Create VMs using the normal spec with `apiVersion: v2.vm.roamvm.io/v1alpha1`.
Set `spec.hibernate: true` to preserve RAM and processes when stopped. The legacy
API rejects this option. Without it, v2 still uses chunked disk checkpoints but
stops and cold-boots the guest normally.

* **Warm:** a retained local PVC contains the writable disk and captured RAM.
  Same-node resume does not download S3 objects. Placement still respects the
  Kubernetes scheduler, PVC topology and resource reservations.
* **Cold:** immutable, verified sparse manifests and content-addressed chunks in
  S3/Garage back writable local caches on another compatible node. QEMU starts
  without reconstructing the entire disk or external RAM file. A private FUSE
  pager fetches and authenticates missing chunks on file reads and mmap faults.
  CPU/device state is downloaded eagerly; RAM is mapped without preallocation.
  A fault fetches its whole content-defined chunk (up to 4 MiB), not just one
  4 KiB page. There is no second-node warm replica or prefetch scheduler yet.

Immutable OCI base images still use Kubernetes image volumes: a node must pull
and unpack an uncached base before QEMU starts. Checkpoint paging does not make
that first base-image pull lazy. Keep common bases cached on eligible nodes when
measuring resume latency; image distribution is a separate startup cost.

New ordinary-memory hibernating guests use private CoW mappings of a named,
read-only RAM file. Live writes stay in anonymous pages instead of causing
filesystem writeback and repeated KVM write faults. Capture stops CPUs and uses
the opt-in `x-roamvm-external-ram` QEMU extension to save CPU/device state without
main RAM. Migration drains the block graph; the runner then copies the actual
stopped child's RAM, including private modifications, through `/proc/PID/mem`
into a new sparse file. It fsyncs RAM and device state before publishing the
capture marker. This requires permission to read the runner's own child, not
general access to other processes. Capturing all RAM is deliberately suspension
work, not startup work. Restore uses `-incoming defer`, not
internal snapshot loading, to prevent initial kernel/ROM loading from overwriting
checkpoint RAM. One authenticated manifest binds disk, RAM and CPU/device state.
Earlier `external-v1` captures retain their shared-mapping path, including fsync
of the mapped inode before publication. QEMU version and CPU compatibility are
still checked; a changed hypervisor requires a compatible checkpoint or an
explicit disk-only cold boot.
Older internal-snapshot checkpoints and hugepage guests retain their eager RAM
restore; their chunked disk can still use the pager.

Each writable cache materializes an overlapping original chunk before accepting
a write. Filled-chunk metadata becomes durable only after the original data does,
so reopening a cache cannot overwrite acknowledged modifications with old bytes.
Before committing the next remote checkpoint, the stopped worker finishes any
remaining reads, then publishes new references before retiring old ones. This
work is on suspension/publication, not the startup path. Local stops can be
resumed while upload is pending. Guest flushes remain enabled. Newly uploaded
chunks are read back and verified before publication; faulted chunks are verified
before exposure. The runner receives only checkpoint-scoped chunks through its
private sidecar socket, not S3 credentials.

All new v2 checkpoints use a bucket-wide shared chunk store (`chunks-v2`). Content
hashes identify reusable data across disks, RAM and VMs. Conditional per-hash
ownership records track VM/epoch references; failed uploads leave discoverable
intents for cleanup. Removing the final reference retires that blob incarnation
before deletion, so delayed cleanup cannot delete identical content reintroduced
by another VM. Local writable caches remain per VM; this is remote deduplication,
not a shared local cache. Existing private `chunks-v1` data remains readable and
is collected when superseded. Do not run an independent bucket GC that ignores
ownership records, or discard the state ConfigMaps while retaining the bucket.

Nodes need the `fuse` kernel module and the v2 device plugin advertising both
`vm.roamvm.io/kvm` and `vm.roamvm.io/fuse`. V2 runners request `/dev/fuse` and
`SYS_ADMIN` to mount their private pager; they do not require privileged mode or
host mount propagation. Apply the updated plugin before scheduling v2 runners.

Hibernation currently requires a root-only guest: no secondary disks, projected
disks, guest ServiceAccount tokens or passthrough devices. Restoring RAM requires
matching QEMU version, CPU identity/features and guest configuration. A mismatch
fails rather than silently discarding processes. Set `hibernate: false` to
deliberately cold-boot the retained disk after changing configuration. Existing
network connections and external sessions are not guaranteed to survive a nap.
A hibernating runner that crashes without a completed RAM capture enters
`RecoveryRequired`; crash salvage must not publish a disk-only success and
silently discard processes. The working disk and last remote checkpoint remain.

## Automatic warm retention

The v2 installation keeps a stopped VM warm for **one hour**, then removes its
local PVC after a verified remote checkpoint exists. The leader checks every
30 seconds. Amp decides when an orb becomes idle and dispatches `pause`; RoamVM
measures retention from that stop, not from guest CPU usage or network traffic.
It never automatically pauses a running VM.

Set controller environment `WARM_CACHE_TTL` to another Go duration (`15m`, `6h`)
or `0` to disable age-based eviction. `WARM_CACHE_SIZE` limits stopped cache
reservations **per node**; the example installation uses `256Gi`, and `0`
disables that limit. Newest stopped caches win. Both controls can act together.
This counts PVC requested/provisioned capacity, not sparse allocated bytes,
live VM storage or OCI image caches. It is not whole-node free-space admission:
configure capacity/quota and image GC in the storage provisioner/containerd too.

Unpublished checkpoints and claims still referenced by Pods are protected, even
if the Pod is unbound or terminating. Eviction commits intent before deleting a
claim and waits for actual deletion before forgetting it. A concurrent wake
either wins before intent or finishes eviction and restores the remote copy;
it cannot start a runner on a disk being deleted. Eviction retains RAM as well
as disk in object storage. Older untimestamped caches get a new retention window.

## Disk-only project clones

A new v2 VM can set `spec.cloneFrom: {name: source, uid: source-uid}` to copy a
durable stopped VM in the same namespace. Use the exact source `spec.image`.
The creation-only reference pins the source UID, so recreation under the same
name cannot supply unrelated data. A copy worker restores the source checkpoint,
exports its current disk without internal snapshots/RAM, and publishes verified
chunk references owned by the destination UID. Once committed, the clone no
longer depends on the source VM's lifetime. Its first start is a fresh guest boot;
subsequent stops can hibernate it normally. Immutable OCI base layers remain
shared by all VMs using that image; identical checkpoint chunks are shared too.

This implementation still exports a disk in a worker; it is not an instant
manifest clone or a reflink across PVCs. Shared references allow independent deletion.
An unfinished clone retries while its source checkpoint remains available;
deleting the source before cloning finishes can prevent completion. Delete the
unfinished destination to clean up its private partial objects and scratch PVC.

## Amp provider

The [Kubernetes Amp provider](../k8s-amp-provider/README.md) packages the dispatch
script, restricted provider RBAC, combined Kustomize entry point and mock-API
proof. Its README covers guest images, orb sizes, bootstrap credentials and
shared remote Nix builders. It reuses this operator and runtime.

## Deletion is destructive

Stopping retains the latest checkpoint. **Deleting a v2 VM deletes its private
objects and releases its shared chunks**. A shared blob is deleted only after its
last reference disappears. The operator first stops the runner and waits for
checkpoint workers to finish/exit, fences further publication, then removes VM
manifests, private chunks, old object versions and ownership metadata. Its
finalizer remains until cleanup succeeds. Empty shared ownership records are
retained to fence delayed operations. Shared OCI bases and chunks still owned by
another VM are not deleted. Legacy VM deletion still retains its checkpoint.

Grant GetBucketVersioning, ListBucket, GetObject, PutObject and DeleteObject for
`vm/` and `chunks/` prefixes, in addition to the existing runtime probe/multipart
permissions. S3 metadata backends also need conditional writes under `shared/`;
the Kubernetes backend stores those coordination records in its state namespace.
Versioned buckets also require ListBucketVersions and DeleteObjectVersion.
Configure lifecycle cleanup for abandoned multipart uploads after hard worker
crashes. An unreachable bucket or denied deletion keeps the CR terminating and
retries; do not force-remove finalizers to bypass cleanup.

Delete all `rvm2` resources and wait for completion **before** removing the v2
operator, its credentials, the state namespace or its CRD. Deleting the CRD itself
is not a substitute for orderly VM deletion. Recovery-required VMs still require
explicit fencing; garbage collection must not bypass split-brain protection.

## Verification

Run `make test` and render `kubectl kustomize config/v2`. On a disposable KVM lab
with the v2 installation and object-store environment configured:

```sh
ROAMVM_TEST_V2=1 STATE_BACKEND=kubernetes STATE_NAMESPACE=roamvm-v2-system \
  go test -tags=integration -run '^Test(Hibernation|WarmEvictionAndDiskClone)$' -count=1 -timeout=20m -v ./test/integration
```

This checks a 512 MiB random in-process payload in a 1 GiB guest, fsynced disk
writes, guest DNS, three warm resumes, cross-node lazy RAM restore with download
accounting, another capture after mutating restored RAM, explicit hibernation
opt-out and deletion of VM objects/metadata. Use the existing startup
benchmark to measure a particular image and workload; latency is not an SLA.

`TestWarmEvictionAndDiskClone` ages a stopped cache using its status timestamp,
waits for the real collector/PVC deletion, and checks RAM/disk preservation after
cold reconstruction. It then boots a disk-only clone after deleting the source
and verifies both source-object cleanup and absence of source RAM in the clone.

For Amp dispatch and guest bootstrap, see the
[provider verification instructions](../k8s-amp-provider/README.md#verification).
